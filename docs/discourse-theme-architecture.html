Discourse Themes & Components — Architecture & Development Workflow

A reference covering what themes and components are in Discourse, how they are implemented, plugin outlets and outlet boundaries, building and using custom components, the settings.yml concept, and the two supported development workflows: pure Ember/Glimmer versus React with Glimmer as the rendering boundary.

1. Discourse Themes Overview

A Discourse theme is not a standalone application. Discourse owns the application shell, routing, data layer, rendering lifecycle, and the build pipeline. A theme injects JavaScript components, CSS, admin settings, and translations into that already-running Ember application. The Theme CLI (discourse_theme watch .) compiles and uploads these assets to the Discourse server.

2. Themes & Components

Inside a theme, UI is built from components. In native Discourse, a component is a Glimmer Component class with an inline <template> block (the .gjs file format). Components hold state, expose derived values through getters, respond to events through actions, and render templates.

2.1 Types of Components in This Theme

Example — tracked state and action:

}

function scrollNext() {
  scrollByPage(1);
}

3. Plugin Outlets & Outlet Boundaries

3.1 What Is a Plugin Outlet

A plugin outlet is a named, predefined insertion point that Discourse exposes inside its own templates. It is the sanctioned seam where a theme can inject custom markup without forking core templates. Discourse decides where the outlet lives and when it renders; your theme decides what renders there.

Examples of core outlet names include above-main-container, below-site-header, discovery-list-container-top, and the homepage block outlet homepage-blocks used in this theme.

3.2 Outlet Connectors (Two Ways to Fill an Outlet)

  1. Template connectors — a file placed under javascripts/discourse/connectors/<outlet-name>/<my-connector>.gjs. Discourse auto-discovers and renders it in the matching outlet.
  2. Programmatic API — an initializer calls a plugin-API method such as api.renderInOutlet(...) or, for the homepage, api.renderBlocks(...).

Programmatic registration used in this theme:

// javascripts/discourse/api-initializers/homepage-blocks.gjs
import { apiInitializer } from "discourse/lib/api";
import BlockHomepageLayout from "../blocks/block-homepage-layout";

export default apiInitializer((api) => {
  api.renderBlocks("homepage-blocks", [
    { block: BlockHomepageLayout, id: "ea-homepage-layout" },
  ]);
});

The array order is the render order. On the native branch this array held two blocks (stat slider, then announcements); on the React branch it holds a single parent layout block that owns one shared React root.

3.3 Outlet Boundaries

An outlet boundary is the contract line between Discourse-controlled rendering and theme-controlled rendering. Everything outside the boundary (mounting, unmounting, route transitions, service availability, compilation) belongs to Discourse. Everything inside belongs to your component. Respecting this boundary keeps the theme stable across route changes and previews.

Owned by Discourse (outside)Owned by your component (inside)
When the outlet element is insertedWhat markup/state renders in it
When the user changes routesDerived data and event handling
When the component is destroyedCleanup logic in willDestroy
Which services/settings existHow those services/settings are used
Theme compilation and uploadComponent internal structure

Why this matters for React: in the hybrid workflow, the boundary is a Glimmer block. React is only mounted after Discourse creates the boundary element, and it is unmounted when Discourse destroys the block. This prevents orphaned React roots during route transitions.

3.4 The Blocks API (Homepage Outlet)

The homepage uses Discourse's Blocks system. A block is a Glimmer component decorated with @block, then placed into the homepage-blocks outlet via api.renderBlocks(). 

@block("theme:ea-demo:homepage-layout", {
  description:
    "Homepage layout that mounts the React game slider and " +
    "announcement components through one shared React root",
})
export default class BlockHomepageLayout extends Component {
  // ...
}

Note: there is no standard admin drag-and-drop editor for these blocks — the array in the initializer is the source of truth for order.

4. Building & Using a Custom Component

4.1 Step-by-Step: A New Block

  1. Create the component: javascripts/discourse/blocks/block-example.gjs.
  2. Register it with the @block decorator.
  3. Add it to the outlet in homepage-blocks.gjs.
  4. Create styles stylesheets/blocks/block-example.scss and import them from _index.scss.
  5. Add any admin inputs to settings.yml.
  6. Add labels/descriptions to locales/en.yml.
  7. Save — the Theme CLI uploads — then refresh the preview.

Minimal custom block:

import Component from "@glimmer/component";
import { tracked } from "@glimmer/tracking";
import { service } from "@ember/service";
import { action } from "@ember/object";
import didInsert from "@ember/render-modifiers/modifiers/did-insert";
import { block } from "discourse/blocks";

@block("theme:ea-demo:example", { description: "Example block" })
export default class BlockExample extends Component {
  @service site;          // injected Discourse service
  @tracked count = 0;     // reactive state (like useState)

  get heading() {         // derived value (like a selector)
    return settings.example_heading;
  }

  @action
  increment() {           // event handler
    this.count += 1;
  }

  @action
  setup(element) {        // runs after the DOM node exists (like useEffect mount)
    this.element = element;
  }

  <template>
    <section class="block-example" {{didInsert this.setup}}>
      <h2>{{this.heading}}</h2>
      <button {{on "click" this.increment}}>Clicked {{this.count}}</button>
    </section>
  </template>
}

Cleanup at the boundary (real example):

@action
mountHomepage(element) {
  this.mountElement = element;
  this.renderReact();
  this.loadHelpData();
}

willDestroy() {
  unmount(this.mountElement);   // tear down the React root
  super.willDestroy(...arguments);
}

4.3 Using a Shared Service (Single-Request Data)

A service is Discourse's equivalent of an app-wide context provider. The eaHelpData service memoizes its fetch so many components share one request: 

export default class EaHelpData extends Service {
  @tracked sectionObjects = null;
  loadPromise;

  load() {
    if (this.loadPromise) {
      return this.loadPromise;   // single-request guard
    }
    this.loadPromise = fetch(API_URL)
      .then((r) => r.json())
      .then((json) => { this.sectionObjects = json.sectionObjects || []; });
    return this.loadPromise;
  }

  get helpByGameCards() {
    const games = this.sectionByType("HelpByGame")?.data?.games;
    return games?.map((g) => ({ title: g.title, link: g.pagePath, image: g.boxArt?.src })) ?? null;
  }
}

Any component injects it and calls this.eaHelpData.load(); only one network request is ever made.

5. The settings.yml Concept

settings.yml declares admin-configurable inputs. Each setting becomes part of a global settings object available to every component at runtime. This is how non-engineers safely control content and appearance without code changes.

Simple scalar settings:

show_breadcrumbs:
  type: bool
  default: true
  refresh: true          # re-render the page when this changes

stat_slider_title:
  default: "Community pulse"

featured_content_max:
  type: integer
  default: 6
  min: 1
  max: 20

5.1 Setting Types

TypeUse
boolToggle behavior on/off.
integerNumeric input with min/max.
string (default)Text; add textarea: true for long text.
enumFixed set of choices.
listSimple repeatable values.
categoriesCategory picker — stores category IDs.
objectsStructured, repeatable records with a validated schema.

Structured objects setting with schema and validation:

announcements:
  type: objects
  default:
    - title: "Apex Legends: Marked Patch Notes"
      subtitle: "Apex Legends"
      size: "big"
  schema:
    name: announcement
    properties:
      title:
        type: string
        required: true
        validations: { min_length: 1, max_length: 150 }
      subtitle:
        type: string
      size:
        type: enum
        default: small
        choices: [big, small]
      image: { type: string }
      link:  { type: string }

5.2 Settings & Locales

Labels and descriptions shown in the admin UI live in locales/en.yml, keyed by the setting name. This keeps the schema and its human-readable text translatable and separate.

5.3 Consuming Settings in Code

Any setting is read directly from the global settings object:

settings.announcements          // array of objects
settings.stat_slider_title      // string
settings.category_sections      // objects with category IDs

Category settings store IDs, not objects. Resolve them through the injected site service: 

categoryUrl(categoryIds) {
  const id = Array.isArray(categoryIds) ? categoryIds[0] : categoryIds;
  return (this.site.categories || [])
    .find((category) => category.id === id)?.url;
}

In this theme, settings also act as a fallback data source: when the API returns no usable game data, the parent block builds cards from settings.stat_slider_display_stats instead.

6. Development Workflows

The theme supports two implementation modes. Both keep Discourse as the owner of routing, data lifecycle, and compilation — they differ only in what renders the visual UI.

6.1 Option 1 — Pure Ember/Glimmer (native)

UI is authored entirely as Glimmer .gjs components. No second runtime, no bundler. Blocks are registered directly into the homepage outlet and use Discourse services and helpers natively.

Development loop:

npm run watch          # discourse_theme watch .

Edit .gjs / .scss / settings.yml / en.yml
  -> Save
  -> Theme CLI uploads the theme
  -> Refresh the Discourse preview   (no build step)

Native homepage registration:

api.renderBlocks("homepage-blocks", [
  { block: BlockStatSlider,    id: "ea-stat-slider" },
  { block: BlockAnnouncements, id: "ea-announcements" },
]);

6.2 Option 2 — React with Glimmer as the Rendering Boundary (recommended)

A single Glimmer parent block acts as the outlet boundary. It fetches/prepares data and then mounts a React tree (Paloma components) into its own DOM element. React is the visual layer; Glimmer remains the integration layer. 

Discourse loads theme
  -> homepage-blocks initializer
     -> BlockHomepageLayout (Glimmer)            <- outlet boundary
          - eaHelpData service -> DummyJSON API
          - settings.yml fallback cards
          - mountHomepage(element, { cards })    <- React entry
               -> HomepageLayout (React)
                    - Paloma Carousel  (StatSlider)
                    - Paloma Accordion (AnnouncementGrid)

Two-terminal development loop:

# Terminal 1 - rebuild React on every src/**/*.jsx change
npm run dev:react       # vite build --watch

# Terminal 2 - upload theme to Discourse
npm run watch           # prewatch hook runs one vite build first

Boundary component: mount and unmount React:

@action
mountHomepage(element) {
  this.mountElement = element;
  this.renderReact();          // mount React only after element exists
  this.loadHelpData();
}

renderReact() {
  mountHomepage(this.mountElement, { cards: this.cards });
}

willDestroy() {
  unmount(this.mountElement);  // avoid orphaned React roots on route change
  super.willDestroy(...arguments);
}

Vite bundles src/ into a theme asset the Theme CLI uploads:

javascripts/discourse/react-dist/ea-react-widgets.js

Clean separation: Discourse service / API / settings concerns live in the Glimmer parent. Visual UI and Paloma composition live in the React children, which only receive prepared props.

Option 1 — Pros and Cons

Pros:

  • Native lifecycle, routing, services, settings, helpers.
  • No second runtime or build pipeline.
  • Smaller deploy surface; no private registry.
  • Lowest risk on route transitions and previews.

Cons:

  • Existing React/Paloma components cannot be reused.
  • React engineers must learn Glimmer/Ember conventions.
  • Design-system components must be recreated.

Option 2 — Pros and Cons

Pros:

  • Reuses Paloma and existing React knowledge.
  • Familiar JSX authoring for rich UI.
  • One shared React root and one data-prep step.
  • Boundary keeps Discourse concerns out of UI.

Cons:

  • Needs Node, Vite, Paloma, private registry access.
  • Two dev processes (Vite watch + Theme CLI).
  • Larger bundle; must mount/unmount correctly.
  • Subject to the 1 MB per-file upload limit.

7. Catches & the 1 MB Per-File Limit

The React workflow is powerful but has real constraints. The most important is Discourse's per-file upload limit of 1 MB (1,048,576 characters). The generated ea-react-widgets.js asset must stay under it or the Theme CLI upload fails.

Error: Value is too long (maximum is 1048576 characters). Fixes, in order of preference:

  • Import Paloma components by exact subpath (avoid barrel imports of the whole library).
  • Enable Rollup chunk splitting so output is divided into multiple files, each under 1 MB.
  • Trim unused imports and dependencies.

Chunk splitting is already configured in vite.config.js:

build: {
  lib: {
    entry: "src/react-entry.jsx",
    formats: ["es"],
    fileName: () => "ea-react-widgets.js",
  },
  outDir: "javascripts/discourse/react-dist",
  rollupOptions: {
    output: {
      chunkFileNames: "[name]-[hash].js",   // split large output into chunks
    },
  },
}

Because the output format is ES modules, each emitted chunk is uploaded and resolved as a separate theme asset, keeping every individual file under the limit.

Other Catches to Know

SymptomCause & fix
Could not resolve ../react-dist/ea-react-widgets Bundle not built. Run npm run build:react; confirm the file exists before the Theme CLI uploads.
ReferenceError: process is not defined A dep uses Node env refs. Vite replaces it: define: { "process.env.NODE_ENV": '"production"' }.
Can't find stylesheet to import Do not import generated Vite CSS from common.scss. Paloma CSS is imported with ?inline and injected once by react-entry.jsx.
default is not exported by Accordion.js Paloma uses named exports: import { Accordion } from "@paloma/core-ui/components/Accordion".
Blank page / extremely narrow cards Paloma Carousel measures its child; give the card a stable width, not an unconstrained intrinsic one.
API requested more than once Keep loading in the shared eaHelpData service; its memoized loadPromise is the single-request guard.
Stale UI after a change CDN caches the old bundle. Hard refresh with Ctrl+Shift+R.

Secrets: the @paloma scope resolves through the EA GitLab registry using GITLAB_NPM_TOKEN from the shell/user environment. Never commit the token to .npmrc, package.json, source, or chat. Rotate immediately if exposed.

8. Architecture Recommendation

Go forward with the React + Glimmer approach (Option 2). Keeping Glimmer as the outlet boundary and React as the rendering layer lets EA reuse the existing Paloma design system instead of recreating every component natively in Glimmer.

Rationale

  • Paloma reuse. Accordion, Carousel, Alert, Badge, Button, Link, Text and other Paloma components are already built, tested, and on-brand. Rebuilding them in Glimmer would duplicate effort and diverge from the design system.
  • The 1 MB limit is solvable. It is a per-file constraint, not a total-size wall. Rollup chunk splitting (already configured) divides output into multiple ES-module chunks, each under 1 MB, uploaded as separate theme assets. Import Paloma by subpath rather than via a barrel to keep chunks lean.
  • Stable integration boundary. A single Glimmer parent plus one React root mounts after the element exists and unmounts on teardown, so route transitions stay clean. Discourse-specific concerns stay in Glimmer; React only receives prepared props.

Action Item for the Paloma Team

Inform the Paloma team that forums.ea.com will now be a consumer of Paloma components. This has concrete implications they should plan for:

  • Bundle-size sensitivity: Paloma is consumed inside a Discourse theme bound by a 1 MB per-file limit. Prefer per-component subpath exports and tree-shakable ES modules; avoid heavy barrel entry points.
  • CSS delivery: forums.ea.com injects Paloma styles via an inline ?inline import (not a global stylesheet). Keep component CSS self-contained and side-effect-free.
  • Runtime assumptions: components run inside a host Ember app, mounted through createRoot into a Discourse-owned element. Avoid assumptions about owning document, global providers, or a dedicated React router.
  • Versioning & peer deps: React/ReactDOM peer versions and Node engine requirements must stay compatible with the theme's Vite build.
  • Coordination: breaking changes to exports, CSS class names, or peer versions should be communicated, since forums.ea.com ships them to end users.

Guardrails When Proceeding with React

  • Keep exactly one Glimmer parent block and one React root for the homepage.
  • Prepare data in the Glimmer parent / shared service; pass props into React.
  • Import Paloma by subpath; never barrel-import the whole library.
  • Check every generated file size before starting the Theme CLI watcher.
  • Before a PR: run npm run build:react and git diff --check, then test a fresh load and a route transition with the console open.
